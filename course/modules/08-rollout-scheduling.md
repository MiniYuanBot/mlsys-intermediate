## §1 一轮 RL 中谁在等待谁

### 1.1 最小训练流水线

一轮基于生成的 RL 常包含 prompt sampling→rollout→reward→行为/目标 logprob 或 value 计算→update→权重同步。不同算法有所不同，但生成长度不均会造成一个共同现象：多数 worker 已完成，更新阶段仍在等少数长任务。

```mermaid
flowchart LR
 P[预先选择 prompt 与 response IDs] --> R[rollout]
 R --> W[reward 与训练所需统计]
 W --> U[policy update]
 U --> S[同步下一版本权重]
 S --> P
```

优化单个 token 的 kernel，未必能消除批次末尾的空闲时间。即使 rollout 完全均衡，总训练时间也不一定改善，因为主要耗时可能来自 reward、权重同步或训练本身。

>

### 1.2 固定任务的时间模型

设任务 $i$ 在同速 worker 上需要 $t_i$ 时间，共 $W$ 个 worker，不能抢占且每个任务只执行一次。任何排程的完成时间 $T$ 都至少满足：

$$
T\ge\max\left(\max_i t_i,\frac{\sum_i t_i}{W}\right).
$$

第一项来自最长任务不能拆分，第二项来自总工作量。如果实验结果低于这个下界，应检查单位和计数是否有误，或实验是否允许了任务拆分、并行。后一种情况已改变前提，不能继续用这里的模型解释。

定义利用率 $U=\sum_i t_i/(WT)$。它只在同速、单任务执行等假设下对应忙碌比例；本实验的 $t_i$ 是模拟 token work units，不能直接说是 GPU utilization。

### 1.3 一个长尾例子

4 个 worker 执行长度 $[700,100,100,100,100,100,100,100]$，总量 1400，平均下界 350，最长任务下界 700。即使其他任务完全均衡，固定不可拆分模型的 $T$ 也不能低于 700，利用率上限只有 50%。

这个例子说明，尾部瓶颈可能来自单个长任务，仅调整排队顺序还不够。进一步改进需要改变任务分块、模型并行或算法分布，同时也会引入新的开销与语义问题。

## §2 预测长度调度：先把一个简单策略写对

### 2.1 List scheduling 的状态

每个 worker 维护预计负载 $L_w$。按一个给定顺序访问 jobs，把当前 job 分配给预计负载最小的 worker，然后把其 estimated_tokens 加到对应负载。输入顺序不变是 baseline；按预计长度降序排序称为这里的 predicted LPT。

实验 `PredictedJob` 只有 id 和 estimated_tokens，调度器看不到 realized length。输出 `Vec<Vec<usize>>` 是每个 worker 的 job ID 队列；每个 ID 必须出现一次且仅一次。

当预计负载相同时，选择编号小的 worker；LPT 长度相同时按 job ID 排序。这些确定性规则便于比较不同运行，也能避免同分时的随机选择干扰归因。

### 2.2 手算 LPT 的非最优例子

输入真实/预计长度都为 $[3,3,2,2,2]$，两个 worker。按 LPT：

| job 长度 | 选择 worker | 分配后负载 |
| -------- | ----------- | ---------- |
| 3        | 0           | [3,0]      |
| 3        | 1           | [3,3]      |
| 2        | 0           | [5,3]      |
| 2        | 1           | [5,5]      |
| 2        | 0           | [7,5]      |

`makespan=7`，但 $[3,3]$ 与 $[2,2,2]$ 的划分得到 6。因此 LPT 是启发式，不是最优解；`a_assign` 验证的是特定算法行为，不是证明最优。

### 2.3 输入顺序不是简单 round robin

lab 的 `lpt=false` 仍把每个 job 放到**预计负载最小**的 worker，只是不重排 jobs。只有所有估计相同时，这种实现才接近按任务数均分的轮转。报告 baseline 时写清楚这一点。

如果评估只用真实长度计算队列时间，真实长度应在 `assign()` 返回以后才被读取。如果在函数内将 estimate 换成真实长度，就已发生信息泄漏，输出表中的 predicted 标签也不能改变这一点。

## §3 预测器的价值如何与调度器分开

### 3.1 历史预测与执行信息分离

A1/A2只从已完成轨迹维护每类有界历史，预测上中位数；cold `start=32`。A benchmark在第100次完成后改变分布，比较window=4/16/64的MAE。实际长度在观测完成之前不可进入预测。

B benchmark固定64个任务，长尾300、其余10–59；`workers=2/4/8`、`quantum=16/64`、steal on/off共12行。在线排程初始estimate恒为32，只有executor知道实际完成长度；偷取决策按队列长度。这样可以把动态工作迁移的效应与预测准确度分开。

后续可以用真实长度构造 oracle，作为诊断挑战；但不能替换上述在线输入后，仍将该策略称为可部署方案。

### 3.2 误差的方向比平均值更重要

低估一个极长任务可能把它与多个其他长任务放到同一 worker，造成长尾；高估短任务可能导致调度偏保守。相同 MAE 的两个预测器，也可能产生不同 makespan。

因此，除平均误差外，还可以按真实长度分组检查误差，画出最慢 worker 的任务组成，并同时分析被低估的长任务与总体误差。这样有助于解释预测误差如何影响调度，避免仅凭预测更准就推断运行更快。

### 3.3 真正预测模型的实验要求

未来接入 prompt 长度、历史生成长度等特征时，训练/校准与测试 prompt 要分开，不能从完成后的生成内容提取在线特征。还要计入预测推理耗时和调度 CPU 成本。

保持相同预测输出，仅替换排程策略，是比较调度器；保持同一策略，仅替换预测器，是比较信息质量。同时更换两者，就难以判断收益来自哪一部分。

## §4 部分 rollout：账本连续不等于模型可恢复

### 4.1 状态清单

一条可恢复生成至少涉及 request/prompt/group ID、已生成 token、位置、KV 或可重建状态、RNG、停止条件、policy version，训练时还可能需要行为 logprob 等统计。

只保存 token 字符串可帮助重建前缀，却不保证和不中断生成拥有相同 RNG 轨迹、数值路径与耗时。采样时恢复随机状态尤其关键。

lab 的 `Segment` 只存 id/group/version/start/tokens/terminal，故其保证是**账本连续和身份一致**，没有实现真实 KV/RNG 恢复。

### 4.2 reassemble 的契约

输入 segments 可以乱序；先按 start 排序，要求首段 `start=0`，后续每段 start 等于当前已收集 token 数；每段 tokens 非空；id/group/version 完全一致；只有最后一段 `terminal=true`。

```text
valid out-of-order input:
  start=2, [12,13], terminal=true
  start=0, [10,11], terminal=false
reassembled: [10,11,12,13]

invalid: start=0, length=2; next start=3 -> gap
invalid: start=0, length=2; next start=1 -> overlap
invalid: terminal=true before the final segment -> terminal conflict
```

`Result<Completed,String>` 要求调用方处理拒绝状态。即使希望尽快开始训练，也不能在输入错误时返回部分 token。

### 4.3 policy version 为什么不可省略

假设前半段由策略 $\pi_7$ 生成，暂停后换成$\pi_8$ 继续，整条响应的行为分布已经混合。若训练仍当成同一版本的 on-policy 样本，算法假设可能不成立。

本实验严格拒绝混合版本。真实异步 RL 可以允许陈旧样本并设计校正方法，但必须明确行为策略、目标策略及允许的延迟范围；删除 version 字段并不能解决这个问题。

## §5 完整 batch、完整 group 与选择偏差

### 5.1 为什么只检查“每组有 G 条”不够

若预定 batch 有 A/B 两组，每组 4 条，A 很快完成，B 很慢；只把 A 的 4 条送去训练，组大小检查仍会通过，但整个 batch 改变了。lab 的 `training_ready` 还要求完成 ID 集合与预先确定的 expected_ids 完全一致。

它同时拒绝重复 ID、未预期 ID、错误 version、缺失任务，以及组人数不是 group_size 的结果。不能通过删除慢任务来缩短 batch 的完成时间，否则就破坏了正确性约束。

### 5.2 当前 API 仍有一个明确边界

这里要分清 B2 与 C1 的检查范围。B2 的 `training_ready` 接收 `expected_ids` 集合，没有保存每个 ID 原来的 group 归属。若两个组互换一个 ID，最终各组人数不变，这一检查可能通过；它也不会核对 prompt 内容。

C1 的 `GroupQueue::push` 已补上本实验的身份规则：`sample.id / group_size == sample.group`，并拒绝重复 ID、已消费 group、超龄或未来版本，以及同组混合版本。`c_queue_admission` 包含 group 错配反例。这是前沿阶段的必修实现，不需要再另写一个验证器才能完成题目。

这条整数映射依赖实验的编号约定：采样时每组固定生成 `group_size` 条轨迹。迁移到真实训练入口时，应保存明确的 `id→(prompt_id,group_id,policy_version)` 清单，不能假设任意框架的 ID 都服从同一编码。

### 5.3 一个选择偏差的数值例子

设同 prompt 四条候选的 `(长度,reward)` 为 $(20,0),(30,0),(100,1),(120,1)$。完整组平均奖励 $\bar r=0.5$。如果只选最快两条，平均变成 0；进一步优势全部为 0，训练信号完全不同。

即便固定保留四条，若先采八条再取最快四条，选择分布仍已改变。只有保证每个预选样本都被执行、保留，单纯重排才容易保持样本集合语义。

B2 用完整 batch 检查固定样本的语义；C 阶段允许按版本陈旧度整组拒绝样本，用学习实验观察这种选择的影响。两阶段的约束不同：C 保证送入更新的 group 完整，却不保证每个预选 group 都参与训练。报告必须保留 `stale_samples`，不能把丢弃旧组解释成纯粹的调度加速。

## §6 从组优势到实际策略更新

### 6.1 本实验的标准化

对于非空的有限奖励 $r_1,\ldots,r_G$，A4 的 `advantages` 先计算总体均值和方差：

$$
\bar r=\frac{1}{G}\sum_i r_i,\quad
v=\frac{1}{G}\sum_i(r_i-\bar r)^2,\quad
A_i=\begin{cases}
0,&v<10^{-20},\\
(r_i-\bar r)/\sqrt{v},&v\ge10^{-20}.
\end{cases}
$$

这里用总体方差，等价于 `correction=0`；分母没有额外加 epsilon。真实框架可能采用不同的标准差约定、归一化方式或 mask，接入时必须逐项对齐，不能将此函数视为所有 GRPO 实现的统一标准。

reward $[0,1]$ 的均值为 $0.5$、标准差为 $0.5$，优势为 $[-1,1]$；$[10,12]$ 也得到 $[-1,1]$。常数组和单元素输入得到全零，空输入返回空数组。`a_advantage` 检查上述两组非恒定输入、常数组与空输入。有限 reward 是输入前提：当前函数没有显式拒绝 NaN/Inf，不能把非有限输入的校验算作已经实现的功能。

### 6.2 带裁剪的策略梯度怎样计算

C3 的 `Policy::update` 确实更新策略参数。实验有 4 类 context、两个动作；每类 context 保存一个 logit $z_c$，选择动作 1 的概率为 $p_c=1/(1+e^{-z_c})$。当动作等于 `context % 2` 时 reward 为 1，否则为 0。

A6 从冻结快照采样，同时保存 `version` 与 `behavior_p`。注意 `behavior_p` 保存的是行为策略选择**动作 1**的概率；若样本实际选择动作 0，计算比率时要取 `1 - behavior_p`。不能在更新时用当前策略概率覆盖它。

设样本实际动作 $a_i$ 在当前策略和行为策略下的概率分别为 $\pi_i$、$\mu_i$，则 C3 最大化组内平均目标：

$$
\rho_i=\frac{\pi_i}{\mu_i},\qquad
J=\frac{1}{G}\sum_i\min\left(\rho_i A_i,
\operatorname{clip}(\rho_i,1-\epsilon,1+\epsilon)A_i\right).
$$

在未被裁剪的分支，单样本对其 context logit 的导数为 $\rho_i A_i(a_i-p_c)$。当 $A_i>0$ 且 $\rho_i>1+\epsilon$，或 $A_i<0$ 且 $\rho_i<1-\epsilon$，目标取常数裁剪分支，梯度为 0。应先用更新前的 logits 累加全组梯度，再除以组大小并做一次梯度上升，最后递增版本。逐条样本立即修改 logit 会改变后续样本的比率，已经不是这里约定的组更新。

按 [c_gradient](../../labs/lab8/tests/contracts.rs) 手算：`context=1`、初始 `logit=0`，均匀数 $[0.1,0.9]$ 采到动作 $[1,0]$，reward 为 $[1,0]$，优势为 $[1,-1]$。此时两个样本的比率都是 1，平均梯度为 0.5；学习率 0.2 更新后 logit 应为 0.1。测试用中心有限差分核对这一导数，还检查常数 reward 的零更新，以及当前 `logit=3`、行为概率仍为 0.5 时两个样本都进入裁剪分支的情况。

这是一项实际执行的 contextual bandit 策略梯度实验，但还没有 token 级序列概率、mask、KL 项或语言模型参数训练。可以对照 [CS336 Alignment](https://github.com/stanford-cs336/assignment5-alignment)，列出需要增加的输入与计算，再进入更完整的 GRPO 训练。

>
> 看 [PPO 原论文图 1（PDF 第 3 页）](https://arxiv.org/pdf/1707.06347#page=3)：左图固定正优势，右图固定负优势，横轴都是概率比率。用 $\epsilon=0.2$ 标出0.8和1.2，并把两图的平坦区对应到 C3 的零梯度分支。不要把“比率越界”一律写成零梯度，要同时看优势的符号。

### 6.3 队列如何影响实际学习

C4 每波从同一策略快照采样 4 个 group，每组 8 条轨迹。B3 执行这些轨迹对应的合成 token 工作量，确定各组的完成顺序；C1/C2 的有界队列逐条接纳样本，完整组才能出队。训练者调用 C3，以学习率 0.3、裁剪参数 0.2 更新策略。队列容量按 group 计，已有组的后续成员不再占新槽；容量不足时由生产者保留并重试，超龄样本则整组拒绝。

每次更新后，版本递增，余下组也随之变旧。例如 4 个 group 都由版本 $v$ 采样，`max_lag=0` 时，第一组更新到 $v+1$ 后，其余组便已超龄。完整 group 检查并不能消除这种样本选择的影响。

`c_learning_closed_loop` 检查 3 个 seed 在 100 波、`capacity=2`、`max_lag=4` 下完成 400 次更新、没有超龄丢弃，并使最终 expected reward 超过 0.85；另有严格 lag 的丢弃反例。expected reward 是按当前策略在四类 context 上精确计算的平均成功概率，不是 batch reward 的噪声均值。

C benchmark 扫 3 个 seed、`capacity=1/2/4`、`max_lag=0/1/4`，共 27 次训练，每次 100 波；输出波 0/9/49/99，共 108 行。updates、backpressure、stale 与 token 工作量都记录累计快照。当前比较固定的是波数，更新次数和 token 工作量可能不同，因此要结合这些计数解释学习曲线。策略采样与梯度更新实际执行，worker 时间仍是事件模型，不能据此声称多 GPU 加速。

## §7 前沿路线：编排、调度与样本分布

[HybridFlow / verl（EuroSys 2025）](https://arxiv.org/abs/2409.19256)是理解 rollout、训练和通信分工的入口。读[固定代码地图](../readings/code-map.md)的训练主入口，画出数据批次与权重版本跨阶段流动，不要仅罗列框架组件。

[DARTS（ICML 2026）](https://arxiv.org/abs/2605.30859)研究主动塑造 rollout 长度分布。其设计涉及样本选择，因此需要同时检查系统效率和学习质量；普通 LPT 实验不能称为 DARTS 复现。

在[公开实现](https://github.com/PKU-DAIR/DARTS)中，从 `OneStepOffRayTrainer`、`_async_gen_next_batch`、`sync_rollout_weights` 开始，区分继承的训练基础设施与论文新增逻辑。阅读产物应回答：何时确定样本集合、谁决定生成预算、哪一步可能使用旧版本权重。

| 路线                  | 改变什么             | 必须守住或重新定义什么   |
| --------------------- | -------------------- | ------------------------ |
| 固定样本的重新排序    | worker 任务顺序      | ID 集合、样本内容、版本  |
| 部分 rollout/恢复     | 任务粒度与状态保存   | KV/RNG/位置/停止条件     |
| 异步训练              | 阶段并发和样本陈旧度 | 行为策略与训练语义       |
| 主动改变长度/选样分布 | 训练数据分布         | 学习目标、质量与公平预算 |

## §8 从 CPU 账本到真实研究

第一步先回答有限问题：固定样本与策略版本时，预测误差怎样影响长尾？在短尾、长尾、双峰三种分布比较 input order 与 predicted LPT，明确 oracle 边界，并做完整性验证。再用 C 的真实采样、组优势与裁剪梯度，观察版本阈值如何改变样本利用率和学习进度。

第二步用单卡小模型采集真实生成长度和耗时。token 数量不能准确代表服务时间，因为长上下文 attention、batching 和 KV 会改变每 token 的成本。拟合时间模型时，应记录这些因素，再用留出的 prompt 检查泛化。

第三步将 C 中验证过的 group、行为概率和版本约束接入真实模型训练，测量调度收益是否足以抵消恢复、队列和权重同步开销。相同 prompt/token 预算、相同更新次数与相同 wall time 是不同口径，应分别报告；不能将 bandit 环境里的学习结果直接外推到 LLM。

候选假设：在固定 batch 语义下，用预测不确定性决定分段或调度，可降低尾部等待，且恢复开销小于节约。该方向与已有 partial rollout 和 tail batching 研究重叠，判断新意时需要具体比较约束和机制。

停止条件：收益只来自真实长度 oracle；削掉难样本后质量下降；恢复成本超过尾部等待；或者生成阶段不是总训练瓶颈。提案中写明这些条件，便于导师判断是否值得投入服务器资源。

> [!question] 随堂自测 D8-8：如何评价研究结果
>
> 1. 两条 C 学习曲线都跑100波，`lag=4` 的 reward 更高。还需要哪些累计计数，才能判断是否只是用了更多样本或更新？应该如何补做公平对照？
> 2. CPU 事件模型中更小 quantum 改善 makespan，接入真实模型后却变慢。给出两个应单独计时的成本，并说明哪种结果会让你停止继续缩小 quantum。

> [!tip]- 核对要点
>
> 1. 至少对照 updates、stale_samples、token 工作量与 makespan；在相同更新数、相同 token 预算或相同墙钟下分别比较，并注明这些口径不是一回事。
> 2. 例如 KV/RNG 恢复或重建、队列/调度开销；也需检查新增同步。若新增成本超过减少的尾部等待，就应停止缩小，保留吞吐下降这一负结果。
