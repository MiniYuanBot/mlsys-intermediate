## §1 一轮到底提交多少 token

### 1.1 正确性契约先于优化目标

一轮提出 k 个 draft token，target 按正确的推测采样规则验证。若接受前 A 个，随后在首次拒绝处提交 correction；若全部接受，则提交 bonus token。因此未考虑 EOS/长度上限时：

$$
N_k=A+1,\quad 0\le A\le k.
$$

这里的“+1”对应验证算法提供的 target token，并非额外假定的产出。若实际引擎因 EOS 提前结束或输出预算不足，N 还应截断；lab 先使用无限可继续生成的简化模型。

控制器可选择 k，但不得改变拒绝采样概率、token tree mask、KV 提交/回滚规则。降低 target 检查精度，或将未验证的 token 直接发给用户，都会改变正确性，超出这里的控制问题。

> [!info] 图解：把一次 verify 对应到提交事件
> 查看 [Leviathan 等人的原始论文 Figure 1（PDF 第 2 页）](https://arxiv.org/pdf/2211.17192)。沿一行标出接受的 draft、拒绝位置和 correction，再把整行改写成 `accepted=A → committed=A+1`。图展示的是论文中的生成例子；颜色不能替代采样正确性证明，也不是本机延迟测量。

### 1.2 用尾概率推导期望，不先假设 IID

对非负整数 A，有：

$$
E[A]=\sum_{i=1}^{k}P(A\ge i).
$$

证明方法很直接：某个样本中 A=3，会在指示量 `1[A≥1]+1[A≥2]+1[A≥3]` 中贡献三次，恰好等于 A；对所有样本取期望即可。

定义条件接受率：

$$
a_j=P(\text{第 j 个接受}\mid\text{前 j-1 个已接受}).
$$

按概率链式法则：

$$
P(A\ge i)=\prod_{j=1}^{i}a_j,
$$

$$
\boxed{E[N_k]=1+\sum_{i=1}^{k}\prod_{j=1}^{i}a_j}.
$$

这不需要各位置独立。`a_j` 本来就是以到达该位置为条件的概率。把各位置无条件接受比例直接代入，会重复计算前缀失败造成的影响。

### 1.3 一次完整手算

设 `a=[0.8,0.5,0.25]`，k=3：

| 接受前缀 A | 概率                 | 提交 N=A+1 |
| ---------- | -------------------- | ---------- |
| 0          | 1−0.8=0.2            | 1          |
| 1          | 0.8×(1−0.5)=0.4      | 2          |
| 2          | 0.8×0.5×(1−0.25)=0.3 | 3          |
| 3          | 0.8×0.5×0.25=0.1     | 4          |

因此 `E[N]=0.2+0.8+0.9+0.4=2.3`。尾概率公式则得到 `1+0.8+0.4+0.1=2.3`，两条独立计算路径一致。

若各位置都为同一 α，可化为几何级数，但 α=1 时不能直接除以 `1−α`。实现使用逐项乘积，既处理非 IID，也自然覆盖 α=0/1。

### 1.4 位置越深，信息通常越少

位置 j 只有前面都接受才有条件观测。即使每个位置条件概率都为 0.8，第 8 个位置被观察到的概率也只有 `0.8^7≈0.21`。较深位置的样本更少，对其概率估计的把握也应低于第一位置。

因此，后续需要讨论置信区间、保守裕量和探索。不过应先保证计数正确，再考虑更复杂的估计器。

## §2 选择 k：收益、成本和可行性必须同时出现

### 2.1 单轮成本模型

令每个 draft token 的成本为 Td，验证 k 个候选的成本为 Tv(k)，CPU 控制/数据准备成本为 Tc(k)：

$$
T(k)=kT_d+T_v(k)+T_c(k),\qquad R(k)=E[N_k]/T(k).
$$

Tv(k) 不必线性或常数。随着候选长度、batch、上下文、shape 和 kernel 路径改变，验证可能跨过不同瓶颈。正式实验应通过测量建立成本表或条件模型；lab 的初始表使用明确标注的假设数值。

`choose_k` 从 `ProfilePoint` 读取 draft 和 verify 成本，另接收概率、bound 与 remaining；教学计算不含控制开销。在 CPU 上测量 choose_k 的耗时后，可以将它作为统一的附加成本进行敏感性分析。如果要引入可变成本，则需扩展接口并更新调用方；报告不能声称现有函数已计入这部分成本。

### 2.2 完整决策表

取 α=0.8、Td=0.08ms、`Tv=[1,1.05,1.15,1.35,1.7]ms`，忽略控制开销：

| k   | E[N]   | T(k)/ms | R(k)/token·ms⁻¹ | 1.4ms bound 下可行？ |
| --- | ------ | ------- | --------------- | -------------------- |
| 0   | 1      | 1       | 1               | 是                   |
| 1   | 1.8    | 1.13    | 1.593           | 是                   |
| 2   | 2.44   | 1.31    | 1.863           | 是                   |
| 3   | 2.952  | 1.59    | 1.857           | 否                   |
| 4   | 3.3616 | 2.02    | 1.664           | 否                   |

k=4 每轮提交最多，却不是速率最高；k=2 在这个模型里最优。表中数值均为教学假设，不能作为任何 GPU 的实测 profile。

>

### 2.3 受约束最优化与不可行返回值

lab 的问题是：

$$
\max_{k\in\{0,\ldots,K\}}R(k),\qquad T(k)\le B.
$$

候选只有少数几个，穷举比复杂优化器更清晰。相同 rate 时选较短 k，减小不必要的 draft 工作。浮点比较容差需固定，不能根据结果临时改规则。

若 `B<T(0)` 且其他候选也不满足约束，正确输出是 `None`。这表示当前成本模型下没有可行方案，调用方必须显式拒绝、排队、降级或者记录违反约束。当前 C 阶段先累计 `infeasible`，再以 k=0 排空请求；剩余 deadline 可能使普通 decode 也不可行，不能把 fallback 记为达标。`remaining=0` 同样返回 `None`，表示已无输出需求；有需求时只枚举 `k≤remaining−1`。

### 2.4 三个会打败直觉的边界

- draft 极慢：即使接受率很高，普通 target decode 仍可能最快。
- verify 在 k=2 发生阶跃：α=1 也不保证 k 越大越好。
- 成本预测低估：预计可行的 k，实测仍可能违约；优化均值不能自动保证尾部。

优化目标决定算法。最大化 E[N]、最大化 E[N]/T、在时间 bound 下最大化 E[N] 是三个不同问题，报告应写出你真正实现的那一个。

## §3 只更新你确实观察到的条件事件

### 3.1 首次拒绝之后是什么

提出 4 个 token，只接受前 1 个，观测序列为：

```text
位置          0        1        2        3
条件事件    成功      拒绝     未观测    未观测
是否到达      是        是        否        否
```

后两个位置是“没有沿接受前缀到达”，不是两次失败。即使 target 一次计算了所有候选 logits，也不能将后缀结果直接视为沿正确接受前缀观测到的条件成功事件，因为条件上下文已改变。

这与生存分析中的截断/删失问题有相似处，但本讲只需要记住：**估计分母只能包含到达该位置的样本**。

### 3.2 折扣计数器的逐步状态

lab 每位置初始 `success=failure=0`。每轮先将所有位置的历史计数乘 λ=0.97，再给已接受位置加一次success，给首次拒绝位置加一次failure。未到达后缀不增加失败：

$$
s_j\leftarrow\lambda s_j+1_{success},\quad f_j\leftarrow\lambda f_j+1_{failure},\quad \hat a_j=(s_j+1)/(s_j+f_j+2).
$$

第一次 `observe(accepted=1,proposed=4)` 后，第0位置为(1,0)，第1位置为(0,1)，后两位置为(0,0)，平滑概率分别为2/3、1/3、1/2、1/2。第二次 `observe(0,2)` 后第0位置为(0.97,1)，第1位置为(0,0.97)，后缀仍无新增观测。第三次 `observe(2,2)` 的状态留作本节自测。

### 3.3 折扣、下界与探索

当前实现按全局 round 衰减所有位置，而非只在某个位置被观测时衰减；即使 k=0，旧证据也会逐渐淡化。随着证据消失，Beta(1,1) 平滑均值会回到 0.5。保守控制还使用 Wilson 形式的下界，零证据时取 0。由于计数经过折扣，且分布可能变化，这个下界不具备置信区间的严格覆盖率保证。

B4实现单侧漂移检测；B5把各请求的升级动作放到共享预算内。B5 的贪心算法有可执行的反例；每次选择最大的边际比值，并不保证整体最优。

### 3.4 控制器决定自己未来看见什么

```mermaid
flowchart LR
 H[过去接受前缀] --> E[条件概率估计]
 E --> K[选择可行 k]
 K --> V[正确的 draft/verify 执行]
 V --> O[可观察前缀和首次拒绝]
 O --> E
```

如果经历一段低接受率后，策略持续选择 k=0，就不会获得新的接受事件。即使环境恢复，它也可能一直无法发现重新推测的收益。这是反馈过程本身的问题，不能简单归因于 EWMA 参数设置。

一个可实验的基线是：每隔固定若干轮，选择一个满足当前 bound 的小 k 做 probe。probe 的机会成本必须计入总耗时，比较策略时也必须保留探索轮。

## §4 round bound 与用户请求 SLO 的距离

### 4.1 一轮提交多个 token 不等于用户平滑收到 token

例如一次验证花 12ms，最后一次提交 4 个 token。`12/4=3ms/token` 是平均产出成本，但用户可能等待 12ms 后收到一批结果。若 ITL 要求每次相邻可见 token 的间隔小于 5ms，是否达标取决于服务流式发送语义，不能直接用 3ms 替代。

请求还经历排队和 prefill：

```text
到达 ── 队列等待 ── prefill ── 首 token ── round1 ── round2 ── 完成
|<---------------- TTFT ---------------->|
                              |<-- 实际 token emission 间隔 -->|
```

TTFT、ITL、请求完成时间以及每轮计算时间是不同变量。lab C 已加入到达、轮级队列与完成事件，输出模拟TTFT/E2E/goodput；它未建模prefill、网络和实际GPU，不能称为真实服务测量。

### 4.2 goodput 需要明确分母和成功事件

一种请求级 goodput 定义是：固定观测窗口中，同时满足预先定义的 TTFT/ITL 要求的已完成请求数，除以窗口长度。若窗口末还有未完成请求，要明确如何处理删失和排空阶段。

本lab的具体达标事件是 `finish<=absolute_deadline`，goodput分母从首个到达到最后完成，包含排空区间。它与同时约束TTFT/ITL的服务定义不同，报告必须明确口径。仅 `committed_tokens/simulated_ms` 仍只是token rate。

### 4.3 Common random numbers 为什么有用

比较固定 k 与 adaptive 时，若每个策略消耗不同数量的随机数，后续看到的潜在事件就不同，差异可能来自负载而非策略。

本版通过 `(seed,request_id,emitted,depth)` 派生随机数；一个策略的调用次数不会推进另一个策略的随机流。这样可以保持潜在随机环境的可比性，但不同策略到达的 emitted 状态仍可能不同；真实 draft/target 也不是这种独立的合成过程。

## §5 前沿系统把哪些问题加回来了

[SpecInfer](https://arxiv.org/abs/2305.09781) 研究 token tree 验证的系统执行；[AdaServe](https://arxiv.org/abs/2501.12162) 进一步面向多 SLO 服务定制推测工作。因此“按 SLO 动态选择推测预算”本身已不是新的研究命题。

| 维度        | 当前 lab                     | 完整系统要考虑                |
| ----------- | ---------------------------- | ----------------------------- |
| 候选        | 单条链，默认k≤4              | tree 宽度/深度及验证布局      |
| 成本        | 合成 draft/verify 表         | batch、context、并发、硬件    |
| 质量/正确性 | 假定正确验证器               | 采样规则、mask、KV 回滚       |
| 负载        | 90请求，三阶段α、到达队列    | 真实trace、混合SLO、batch并发 |
| 控制        | 单请求枚举、独立共享预算练习 | 多请求共享资源和预算          |

[AdaServe artifact](https://github.com/zikun-li/AdaServe-Artifact-Evaluation) 的公开完整实验配置面向 A100 多 GPU；在本机上先阅读配置、定义和成本构成；不能将完整系统简化为同名 toy benchmark，就视为完成复现。[固定版本源码入口](../readings/code-map.md) 记录了 artifact 与子模块的边界。

## §6 从教学控制器走向可讨论的研究问题

一个适合本机起步的问题是：**在部分观测和接受率漂移下，带有限探索与保守成本裕量的控制，能否比固定 k 和纯折扣估计更快恢复，同时控制违约率？** 先查已有 adaptive speculation/online control 工作，再判断是否有新的约束或机制。

实验按证据强度逐步升级：

1. 合成 high→low→recovery，验证估计偏差和停止探索失败；
2. foundations 引擎采集真实接受前缀、draft/verify 成本，分别校准与评测；
3. 加入真实到达和并发，测 TTFT、ITL、goodput、CPU 控制成本；
4. 与最近邻完整系统对照，说明仍未覆盖的硬件/模型范围。

停止条件也应明确：只有 oracle 有收益；探索成本大于恢复收益；成本估计误差压倒策略差别；或者机制与最近工作没有可说明的差异。即使停止，也应在报告中说明缺少哪类信息，以及它如何导致失败。

> [!question] 随堂自测 D4-6：设计能推翻假设的实验
>
> 1. B benchmark 固定每轮观测 proposed=4；C 的观测由控制器动作决定。仅凭 B 的 high→low→recovery 曲线，能否证明控制器在线恢复？
> 2. 你增加 periodic probe 后 goodput 提高。列出至少两项必须保持一致或计入成本的条件，并给出一个停止继续扩展的判据。

> [!tip]- 核对要点
>
> 1. 不能。B 比较相同外部证据下的决策；C 才能暴露停止推测后失去观测的问题。要在 C 保留 no-probe 对照并记录 probe 的实际开销。
> 2. 至少固定到达 trace、成本表、deadline、配对 seed，并计入探索与控制成本。若计入这些成本后收益消失，或只有 oracle 有收益，应先停止扩大实现范围。
