# 八个方向的选题与硬件地图

[课程索引](../index.md)

你在数学、系统基础和执行力方面有优势，也能稳定投入约 36h/周。接下来需要建立研究中的反馈：将读懂一个领域的目标，拆成每周测出一个能解释的现象。现阶段可优先选择**单机就能验证核心机制、成功失败都能提供信息、与现有组内工作有关联**的题目。

以下判断是课程设计建议，不是对新颖性或发表概率的承诺。苗老师公开工作覆盖推理、编译、训练、数据管理；具体题目是否与组内正在进行的课题重复，仍需通过组内讨论确认。[教师主页](https://hsword.github.io/)、[论文目录](https://hsword.github.io/publications/)。

| 优先级 | 足够具体的切入点                          | 本机最小实验                                 | 值得研究的条件变化                      | 最近邻/竞争方法                         | 升级条件                              |
| ------ | ----------------------------------------- | -------------------------------------------- | --------------------------------------- | --------------------------------------- | ------------------------------------- |
| A      | D1：按层/头/阶段分配 KV 精度与保留预算    | K/V 小矩阵；0.6B 的真实 K/V；上下文 512–4096 | 长短上下文切换时，固定预算是否失配      | KIVI、PQCache、FlashInfer               | 多模型/长上下文质量评测需 24–80GB 卡  |
| A      | D3：动态 batch/shape 下是否值得编译与融合 | RMSNorm/residual；变长序列；冷启动与稳态分开 | 小请求数量、分布漂移下的总完成时间      | torch.compile、Mirage/MPK、Event Tensor | 最终需真实 serving trace；不必先多卡  |
| B      | D4：观测有噪声时的 SLO 推测预算           | Rust 策略回放；0.6B/1.7B 验证成本曲线        | 接受率漂移、验证耗时非线性、队列压力    | AdaServe、SpecInfer、引擎自适应推测     | 高并发/大模型需要组内 GPU             |
| B      | D5：多租户共享前缀的缓存准入与公平性      | prefix trace、引用计数；单卡真实 TTFT        | 热点迁移、长前缀占满缓存、不同租户 SLO  | SGLang、LMCache/CacheBlend              | 有代表性的请求 trace 比多卡更先要解决 |
| B      | D7：专家预取的净收益与污染控制            | 合成路由、微型专家矩阵、真实 H2D             | 热点变化、错误预测、带宽与缓存竞争      | MoE-Infinity；完整框架的 expert cache   | 真 MoE 权重还受主机 RAM/磁盘约束      |
| B      | D8：不改变采样语义的 rollout 长尾调度     | 长度 trace、分段账本、组完整性检查           | 长度预测误差、策略滞后、异步恢复        | verl/HybridFlow、DARTS                  | RL 学习曲线的多 seed 验证通常要多卡   |
| C      | D2：小 batch/不规则形状的低比特解包融合   | 4060 上 CUDA/PTX GEMV，形状与 group sweep    | metadata 开销、寄存器压力、调用次数变化 | AWQ、QServe/OmniServe、已有量化 kernel  | 强工程竞争；需超越朴素 baseline       |
| C      | D6：PEFT 的激活预算与重计算策略           | 微型 LoRA 网络、逐层重计算、梯度等价         | 序列长度波动、训练/推理共存预算         | QLoRA、checkpointing、FlexLLM           | 真训练质量/共服务实验要更大显存       |

A/B/C 表示**起步推荐等级**，不用于排列领域的学术价值。如果特别喜欢底层代码，可以把 D2 作为主选；如果对 RL 更有动力，可以优先浏览 D8，但纯调度模拟不能作为 RL 收敛结果。

## 硬件边界与起步配置

| 设备                                             | 现在适合做什么                                                               | 不能据此推断什么                                                            |
| ------------------------------------------------ | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 16GB 统一内存 Mac mini                           | 阅读、C++/Rust CPU 测试、trace 回放、数据分析；若为 Apple Silicon 可另测 MPS | 统一内存不等于独立 16GB CUDA 显存；MPS 性能不能替代 NVIDIA kernel 结果      |
| RTX 4060 8GB，Windows + WSL2                     | CUDA/PTX、torch.compile、0.6B/1.7B 短上下文、微型 LoRA                       | 不能把 H100 的 FP8/TMA/多卡通信结果按比例搬来；不承诺任意 7B 模型训练可运行 |
| Intel UHD                                        | 日常显示；CPU 程序与文档                                                     | “128MB”不代表可与 NVIDIA 显存合并用于 CUDA                                  |
| [北大 HPC](https://hpc.pku.edu.cn/) / 组内服务器 | 在研究问题确认后做规模与可迁移性验证                                         | 本次未确认账户资格、可用 GPU/分区/价格/配额；不预设已经可申请               |

建议起步预算：CUDA microbench 常低于 512MiB；lab6 微型网络以实际峰值为准。0.6B FP16/BF16 权重理想体积约 1.2GB，1.7B 约 3.4GB，另需 KV、临时工作区、框架和 CUDA context。先将 `batch=1,input<=512,output<=64` 跑通，再逐级扩大；实际可用显存低于 8GB。

KV 估算使用模型 config 的 `num_key_value_heads`，不能把 query heads 当成 KV heads。训练预算还包括梯度、优化器状态和激活；全参数 Adam 与冻结基座的 LoRA 不同。macOS CPU 测试在本次交付中未实机验证，见 [验证边界](../../labs/docs/validation.md)。

## 选题打分：用证据替代“看起来热门”

每项 0–2 分：兴趣、两周内基线可运行、可用 workload、能写出反证条件、与导师工作契合。**新颖性需要对照已有工作判断**：另列最近三篇论文，逐项比较场景、约束、机制和评价。无法说明差异时，先做复现与测量，不能将其称为新算法。

三条最适合带去讨论的候选假设：

1. **H-KV**：相同总缓存字节预算下，按离线校准的头敏感度分配精度，在跨任务 held-out 集上比统一精度有更好的质量—延迟折中。先排除已有 mixed-precision KV 工作；需要算上量化、检索和索引开销。两周内若真实质量代理不稳定，停止增加策略复杂度。
2. **H-Compile**：基于请求 horizon 和形状漂移触发的有限专用化，在含冷启动的总时间上优于 eager、静态编译、dynamic compile 和固定 bucket。动态分桶已有相关工作，不能仅凭采用这一机制声称创新；差异需要来自新的目标、约束或能解释的反例。如果收益只在不合理地重置编译缓存时出现，应放弃这一假设。
3. **H-Spec**：在接受率估计误差下保守分配推测预算，能改善满足 TTFT/ITL SLO 的 goodput，而不是只提高接受 token 数。先与 AdaServe 的问题定义逐项比对；若控制开销或估计滞后抵消收益，报告负结果。

## 申请服务器前的一页说明

- 本机复现了什么，原始数据在哪里；哪个结论尚不成立？
- 需要验证的唯一规模变量是什么？为什么本机不够？
- 请求的 GPU 显存/数量、主机 RAM、数据集与磁盘、预估 GPU-hours、停止条件。
- 队列系统、允许的容器与网络、存储路径和使用政策，以实际平台说明为准。使用 Slurm 前需核对分区名，不能直接照抄不存在的名称。
